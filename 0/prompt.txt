2. **Key Technical Concepts:**
   - **GRPO advantage computation is per-prompt-group and relative.** TRL `grpo_trainer.py:2177-2199`:
     ```python
     mean_grouped_rewards = torch.nanmean(rewards.view(-1, num_generations), dim=1)
     mean_grouped_rewards = mean_grouped_rewards.repeat_interleave(num_generations, dim=0)
     ...
     advantages = rewards - mean_grouped_rewards
     if self.scale_rewards != "none":
         advantages = advantages / (std_rewards + 1e-4)
     ```
     The mean subtracted is the **group's own** mean. `scale_rewards` defaults to `"group"` (`grpo_config.py:218`), and the repo never sets it, so std is per-group too. A group whose rollouts all score alike yields exactly zero advantage — the numerator is zero, and the `+1e-4` only guards the division.
   - **Cross-group variance NEVER reaches an advantage.** A batch with one all-correct group and one all-wrong group still produces zero advantage on both. This corrected a wrong claim in my own earlier RUNNING.md writing.
   - **Why raising `batch_size` works:** an optimizer step accumulates gradient over every group in the batch, so it is dead only when *all* of them are internally uniform. At a per-prompt saturation rate of 0.46: bs=1 → 46% dead, bs=4 → 0.46^4 = 4.5% dead, bs=8 → 0.46^8 = 0.2% dead.
   - **`batch_size` is not the memory knob.** At `batch_size: 4`, `n_rollouts: 8`, `micro_batch_size: 1`, a step is 32 completions pushed through the model one at a time with `gradient_accumulation_steps=32`. Training-side memory never constrains `batch_size`; only vLLM's generation pool grows with it, capped by `gpu_memory_utilization`, so it queues rather than OOMs.
   - **The asymmetric confound:** `env_reward` is binary, so groups saturate ~46% of the time. `CosineLengthReward` is continuous in completion length, and 8 rollouts of one prompt have 8 different lengths, so it rarely saturates. At bs=1 that difference *is* the training signal.
   - **Steps-vs-prompts tradeoff:** at a fixed prompt budget, a larger batch buys gradient quality by spending optimizer steps. 600 prompts = 150 LoRA updates at bs=4, 75 at bs=8. This setup is step-starved, not noise-starved.
   - `AdvantageWeightedComposer` also z-scores per group and skips components with `std < 1e-6`, so a uniform group is zeroed twice (composer, then TRL). The composer is not the culprit; TRL alone would kill it.
   - Cosine arms measured 71-79% gradient coverage rather than 100% because cap-saturated completions have identical lengths, tying back to the separate truncation-confound finding.
